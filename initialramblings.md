This is a fascinating reverse-engineering challenge. You are entirely correct that this is inherently a lossy transformation (the classic "hamburger back into a cow" problem), but since we control the rendering environment, we can absolutely cheat.

Because you are working with minijinja (and likely Rust, given the ecosystem), we can leverage both the engine's internals and some clever text-processing heuristics to build a highly confident "source map" for your text file.

Here is a playbook of heuristics and instrumentation strategies to maximize the changes you can successfully map back to the template or variables.

1. The "Shadow Render" (The Source Map Approach)
This is arguably the most powerful heuristic. Since you control the rendering step, you don't just render the file once; you render it twice.

Render A (Production): The normal expansion with actual variables. This goes to your downstream tools.

Render B (The Shadow Map): You pass a mock variable dictionary where every value is replaced by its own access path or a deterministic UUID. For example, user.name doesn't resolve to "Arthur", it resolves to __VAR_USER_NAME__.

How it works for diffing:
When the downstream tool modifies Render A, you do a standard diff between the Original Render A and the Modified Render A.
Let's say the diff says: Line 14, characters 10-20 changed from "Engineer" to "Lead Eng".
You then look at Line 14, characters 10-20 in Render B. If that exact spatial location contains __VAR_ROLE__, you can assert with near 100% confidence that the downstream tool intended to update the role variable, not the static template.

1. Custom Formatters (The Invisible Boundary Injection)
If maintaining a perfectly parallel Shadow Map is too brittle (e.g., variable lengths change the character offsets, breaking spatial mapping), you can instrument the output directly using minijinja's formatters.

minijinja allows you to set a custom formatter via Environment::set_formatter. You can intercept every single variable expansion and wrap it in invisible metadata.

If the output is HTML/XML: Inject comments: Arthur

If the output is raw text/code: Use Zero-Width Characters to encode metadata, or language-specific comments if you know the target syntax.

When the downstream tool modifies the file, you parse the file for these boundaries. If the text between the boundaries changed, the variable changed. If the text outside the boundaries changed, the template changed.

1. Static Anchor LCS (Longest Common Subsequence)
If you cannot modify the output (meaning no injected comments) and the Shadow Map is out of sync, you fall back to algorithmic heuristics.

You can extract all purely static text chunks from the original minijinja template (everything outside of {{ }} and {% %}). These become your Anchors.

Run an LCS algorithm to find these Anchor chunks in the modified output file.

If an Anchor is missing or mutated, you flag a Template Change.

If the Anchors are intact, but the "meat" between them has mutated, you cross-reference the gap with the variables passed to that specific block.

1. Bi-directional Value Fingerprinting
If a tool changes a value, and you need to figure out which variable it was supposed to be, you can use the original variable state as a search index.

Create a reverse index of your variables: {"Arthur": "user.name", "Engineer": "user.role"}.

Diff the Original Render and the Modified Render.

Identify the deleted text (the text that was replaced).

Look up the deleted text in your reverse index.

Heuristic Catch: If the value is a boolean (true/false) or a common number (0, 1), this yields low confidence. If the value is a highly specific string (like a URL or a unique name), confidence approaches 100%.

1. AST-Aware Diffing (The Advanced Route)
Since you are likely in Rust, you can parse the template using minijinja's parser to get the AST (Abstract Syntax Tree).
Instead of diffing lines, you diff logical blocks. If the downstream tool modifies a block of text that the AST tells you was generated by a {% for %} loop, you know that the change cannot be applied to the template as a simple text replacement.

Heuristic rule: If a change occurs inside a repeated loop block, it must be mapped to a change in the underlying Array/List variable, not the template itself.

Summary of the Best Workflow
If I were building this to be as robust as possible, I would combine 1 and 2:
Write a custom minijinja formatter that wraps variables in a non-destructive identifier (like a specific comment syntax if the format allows, or invisible unicode tags if it must look like plain text to the downstream tool). When the file comes back, run a regex to extract the tags and their inner contents. Compare those to the original variables. Everything else that changed is a template diff.
